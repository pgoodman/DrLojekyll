# Testing and Grounding Audit

The repository's testing discipline is a major asset. The main risk is not a
lack of tests; it is treating all green tests as equally independent evidence.

## Evidence Ladder

### Strongest: independent semantic comparisons

- The oracle compares incremental derivation-counter evaluation with a
  from-scratch stratified evaluation after each batch.
- Monotone projections provide another semantic view for selected cases.
- Equivalence gates run flat and keyed-instance lowerings with the same driver
  and compare observable output.
- Runtime drivers contain explicit expected-result assertions in addition to
  stdout goldens.

These catch wrong answers, not merely text drift. They still share the parser
and Query construction, so they are not independent of front-end bugs.

### Strong: structural invariants with independent recomputation

- Rel validators recompute expected op sets/dependencies and abort on mismatch.
- DataFlow provenance validators check sound structural properties.
- `.irgold`/`.df`/`.rel` pins protect selected lowering shapes.
- Four optimization modes expose pass-order and accidental-dependency bugs.

These are excellent for detecting architectural drift when the expected
property was hand-derived first.

### Moderate: committed observable goldens

OptDiff compiles and runs 178 driver-bearing cases in four optimization modes
and compares each stdout against a committed golden. This catches configuration
divergence and broad regressions. A golden initially generated by the same code
is not an oracle until reviewed against an independent expectation.

### Weak alone: self-consistency and prose records

- A census matching another census derived from the same graph.
- A generated golden blessed without a hand prediction.
- A measured table whose driver is untracked.
- Multiple design documents agreeing with each other.

These can support stronger evidence but do not establish correctness alone.

## Automation Gap

The default CI workflow builds Debug/Release and runs CTest. CTest currently
registers six targets. It does not register the OptDiff suite. The strongest
manual suite is therefore absent from the normal automated gate.

The fuzz workflow is named `.github/workflows/fuzz.yml_`, so GitHub Actions does
not run it. It also uses old `ENABLE_*` CMake variables instead of the current
`DRLOJEKYLL_ENABLE_*` variables. Re-enabling the file without repair would not
exercise the intended configuration. The fuzz CMake names a nonexistent
`BackendFuzzer.cpp`, and the parser target's claimed format/reparse property is
inert: it formats nothing and reparses the original input. See
[`test-coverage-gaps.md`](test-coverage-gaps.md) for the code-derived diagnosis.

Disposition: **Fixable, but separate from CostModel slice 1.** Add an automated
OptDiff CI job with an appropriate shard/time budget, and repair/re-enable the
fuzzer only after verifying its current target and corpus. Do not make the
CostModel implementation wait for CI restructuring, but do not claim these are
standing automated gates until they are.

The full OptDiff inventory, sparse feature intersections, pass-management
matrix gaps, and weaknesses in the application tests are recorded separately
in [`test-coverage-gaps.md`](test-coverage-gaps.md).

## Harness Configuration Audit

The pass harness is actively useful for experimental A/B and evil-monkey
testing, so configurability has a current owner. Two problems remain:

1. `df.sink` is registered and advances the bisect counter, but its entire body
   is commented out. It is a fake experimental dimension.
2. Compatibility aliases and comments disagree about whether
   `df.ident_join` is part of `-disable-dataflow-opt`.

Disposition: **Fix now or immediately after the CostModel adjudication.** Delete
`df.sink` from the registry and pass driver until there is live code. Make one
authoritative pass list generate alias behavior/help, or update all call sites
together. Do not keep old and new semantics in parallel.

## CostModel Test Matrix

The first calibration must include all of these:

| Test | Purpose | Independent authority |
|---|---|---|
| Hand-counted exact mono delta | Prove one supported rule | runtime counter site + arithmetic |
| Recognizer on/off, four modes | Config invariance and structural delta | current compiler/run outputs |
| Duplicate-row negative witness | Refute `idx_adds = incoming rows` | runtime counters |
| One multi-index or no-index witness | Expose index multiplicity | generated schema + counters |
| Changed fanout sweep | Check scaling law, not one point | generated concrete data |
| Held-out input sizes/keys | Detect fit-to-calibration | measured runner |
| Unsupported-field assertion | Prevent silent zero predictions | report type/unit test |

Before treating optimized Query shape as stable test input, also record why
canonicalization terminated. A golden produced after a silent iteration-cap
exit is reproducible output, but it is weak evidence for a claimed optimizer
fixpoint.

For exact fields, compare integer equality. For estimated fields, record the
error metric and report the result; do not make the first slice green by adding
a broad tolerance.

## Reproducibility Requirements

Every measured claim must record or generate:

- the `.dr` source and exact compiler flags;
- the concrete input event trace and initial state;
- generated-code compiler flags;
- the counter-enabled binary identity;
- the before/after snapshot boundary;
- expected fields and why each is exact or estimated;
- a command that reruns the measurement from tracked files.

The measurement binary must remain separate from timed performance binaries,
but the separation should be encoded in build targets rather than remembered
only in prose.

Release tests are necessary but not sufficient: internal correctness checks
implemented only as `assert` do not execute under `NDEBUG`. A release success
must not be described as stronger evidence than the validations actually
present in that binary.
