## R1 — ORDER OF DIFFS

**Question.** In what order do the R-final diffs land: the folds, the per-join
emission op, the direction flip, the rename? The lanes split: a2 + a4 say
**emission-op BEFORE flip**; a1 says **flip-first**.

**Decision inputs.** The emission op's drain-order key (`emit_walk_seq`) is
byte-LOAD-BEARING: drain order determines next_id allocation → generated bytes (a2
§3.1; BuildJoin id-mint Join.cpp:313). `walk_seq` is a work-list SCHEDULE artifact
(Build.cpp:1010-1022) — a3 PROVED that class of order is NOT flow-reproducible (0 of
11 carriers). By contrast the eager MARKER order is order-free under the count oracle
(re-bless absorbs it, §R2). The folds touch neither the DR flow model nor the markers
(a4 — independent). BuildJoin has exactly 2 callers (verified), so the emission op is
a bounded change.

**RECOMMENDATION — `Fold A → Fold B → emission op (kJoinEmit/kProductEmit) → flip →
rename`.** [Overrides a1's flip-first on the emission-op-vs-flip sub-question; a4 + a2
agree.] Grounds: the emission op's order key can ONLY be captured walk-side (the walk's
emplace_back counter at Join.cpp:764) — it is a scheduler artifact with no flow-side
derivation, exactly like the marker order a3 proved non-reproducible, but UNLIKE the
markers its order is byte-load-bearing and cannot be re-blessed away. So it must be
built while the walk-side capture machinery exists, proven byte-identical, and only
THEN should the flip retire the marker record/replay (the walk-side `walk_seq` capture
is a separate, surviving signal the flip does not touch). a1's flip-first under-weighted
that the emission op's order is byte-load-bearing (it treated emission enrollment as
absorbable like the markers). Folds go first because they are the cheapest, lowest-risk
items and shrink the join body the emission op then models — one re-bless of the join
carriers, not two. The rename is cosmetic and goes last regardless.

**Pre-commits downstream.** The flip inherits a substrate with BOTH join halves modeled
(kEagerJoin marker + kJoinEmit emission). The flip's post-flip enrollment of the
emission op is flow-derived from dr_flow.joins (delta) + the eager subgraph (eager) —
the same reachability the flip already computes — so absorbing it is not new coupling.
The join carriers (join_1, demand_tc, optimize_2, d5, symrec) re-bless twice total
(once at the emission op for the new census line + kJoinEmit blocks, once at the flip
for marker order) — accepted.

## R2 — THE FLIP'S ORDER CHOICE + GATE FAMILY + IDENTITY RESOLUTION

**Question.** (a) Reproduce the walk's op.N order by scheduler-replay, or enroll in a
canonical flow order and re-bless the 11 `.deltarel` pins under a structural gate? (b)
Which enrollment key? (c) Pre-registered gate family per sub-diff? (d) Per-edge
identity: counted-consume or a new per-edge key?

**Decision inputs.** THE load-bearing fact: `key_of` is DUMP-AND-VALIDATOR ONLY —
"emission never reads this key" verbatim at DeltaRel.cpp:4672 + 4689 (consolidator
confirmed). So enrolling in any order is EMISSION-byte-safe; only the dump labels +
intra-band order move. a3 proved NO natural flow order reproduces the walk (0/11;
detord 116 relabels/20 band-reorders, depth 100/12). Scheduler-replay would re-import
exactly the Build.cpp↔DeltaRel coupling the flip exists to delete. Because key_of
always sorts the lead-0 band by (table_id, oi), the render depends ONLY on the
within-band construction order — so the enrollment key's whole effect is that
secondary order, and a3's depth measurement is the decision-relevant number.

**RECOMMENDATION.**
- (a) **Derivation-order enrollment + re-bless (option-2), NOT scheduler-replay.**
  Grounds: §0 PROVES it is emission-safe; scheduler-replay re-imports the coupling the
  flip deletes and is self-defeating; permcheck already mechanizes the order-free bless;
  option-2 is a strict determinism improvement (the dump order becomes a pure graph
  function, retiring the work-list schedule from the observable surface).
- (b) **Within-band order key = `Depth` (tiebroken by `DeterministicOrder`).**
  [Resolves a1 table-major vs a3 depth: they optimize different axes and compose — a1's
  table-major grouping is orthogonal (key_of already groups by table_id on render); the
  decision-relevant knob is the within-band secondary key, and a3 MEASURED depth as
  lowest-churn: 100 vs 116 relabels, 12 vs 20 band reorders, 4 carriers pure-relabel
  (negate_1/6, d5, map_3).] Depth's std::sort ties are unspecified → the
  DeterministicOrder tiebreak is mandatory for determinism.
- (c) **Gate family, pre-registered per sub-diff** (a1 §5 + a3 §5): SD-1 (de-dup cut
  predicate) + SD-2 (relocate ClassifyEagerSink) = **BYTE** (emission + dump both
  unchanged — same predicate/value at this step). SD-3 (the flip core) = **STRUCT** =
  emission-.h/.cpp byte-identity (HARD, the 844-row A/B) + census-equal (the 27-kind
  line byte-identical on all 11 pins) + a per-lead-0-band order-free multiset re-bless
  (permcheck-style, scoped to the eager sign-0 band ONLY — ingest folds keep op.0/op.1,
  INGEST_LOOP untouched); the 3 pure-relabel carriers bless under a pure label-remap
  check, the 8 block-reorder carriers under the per-band multiset compare. SD-4 (count
  oracle) = **VALIDATOR-ONLY** (prove live by perturbing the derivation → abort).
- (d) **Counted-consume (i), NOT a per-edge key.** Grounds: the emission is edge-
  multiset-valued but the dump is already view-valued-with-repeats; (i) preserves that
  exactly (byte-compatible), needs no pred_view, no dump-grammar change, no E-71 lane;
  the count oracle supplies the only cross-check (i) lacks. (ii) per-edge key buys
  observability at an E-71 grammar lane + larger re-bless — deferred to a future OD slice.

**Pre-commits downstream.** The one-time 11-pin re-bless under permcheck+census-equal;
the count oracle (R4) is SD-3's compensating control and MUST land with it. The dump
order becomes canonical (Depth-ordered), decoupled from Build.cpp's scheduler. §7d
stays (see R2-note). Note: the per-edge provenance question stays open for a future OD
observability slice.

## R3 — THE PER-JOIN EMISSION OP: REFERENT / PAYLOAD / COUNT LAW / TABLEINDEX CARVE

**Question.** What is the op's referent, payload, count law, and how is the non-constant
per-join id budget handled?

**Decision inputs.** TABLEJOIN mints once per BuildJoin call (Join.cpp:313), SHARED by
eager (Join.cpp:601) + delta (Stratum.cpp:1532) — a 2-caller M13 sweep (verified).
TABLEPRODUCT mints at the SOLE Product.cpp:148 (verified — no delta path, no M13). The
per-join next_id budget is `1×TABLEJOIN · |pivots|×pivot_var · k×TABLEINDEX ·
Σout×out_var`, and `k` is NON-CONSTANT: GetOrCreateIndex (Data.cpp:348-364) reuses an
existing column-spec for 0 ids, so `k` depends on GLOBAL emission order.

**RECOMMENDATION.**
- **Referent**: one op per **(emitting proc/section, join_view, path-form ∈
  {eager,delta})** = 1:1 with a BuildJoin call. Family: `kJoinEmit` + sibling
  `kProductEmit`, ONE slice, **census 27 → 29**.
- **Payload**: `emit_join_view`, `emit_form`, `emit_order_key = ContinueJoinOrder(view)`,
  **`emit_walk_seq`** (NEW — the emplace_back counter at Join.cpp:764; the drain-order
  tie-break the priority integer lacks, because ContinueJoinOrder COLLIDES on equal-
  depth joins), `emit_stratum` (delta). NO stored table (render `table=` re-derives via
  ModelTableOrNull, E-107). Effect-FREE at flow layer, NOT id-neutral at lower (M17).
- **Count law**: DELTA `expect(kJoinEmit_delta)` from dr_flow.joins (flow-derivable);
  EAGER `expect(kJoinEmit_eager)` per (proc, distinct reached join_view) — ALSO flow-
  derivable, so unlike the 8 markers it carries a scalar expect(), closing part of the
  ADJ-S12 gap at the emission layer. Site-5 key multiset (join_table_id, form, order,
  walk_seq) — a SET (walk_seq unique), tighter than the marker A.6(c).
- **TABLEINDEX**: **CARVE-3** — EXCLUDE indices from the op's id contract. The op covers
  only {TABLEJOIN, pivot_vars, out_vars}; GetOrCreateIndex stays a shared CSE side-stream
  OUTSIDE the contract (byte-identical by construction because the lowering calls the
  untouched builder). Grounds: preserves the byte-move property, refuses a false constant
  budget, matches the M17 precedent (count law keys on the op's own discovery inputs —
  indices are a shared CSE resource, not a join discovery input). CARVE-1 (model index as
  a stream) is out-of-scope program-wide index-CSE modeling; CARVE-2 (canonicalize
  provisioning) CHANGES the next_id stream → converts a byte-move into an emission-shape
  re-bless, the exact thing the op must avoid.

**Pre-commits downstream.** Lowering: BuildJoin becomes the body of a thin
`LowerJoinEmit` pass-through (byte-move at the drain) both callers route through — the
M13 discharge; kProductEmit wraps the sole Product.cpp:148 site. An E-71 grammar lane is
owed for the new render tokens (see R3-note). Pre-flip the op mints walk-side and
replays via the existing machinery (R1); the flip converts enrollment to flow-derived.

**R3-note (E-71 lane).** The op renders in the dump (it is a flow.op) → needs a new
KindName + a DEDICATED render case with new tokens `form=`/`order=`/`seq=`. This is a
render-grammar addition → E-71 pre-code adjudication REQUIRED (the R2 cmp=/functor=
precedent). Recommend SURFACING order=/seq= — the whole point of modeling the deferred
emission is to make its order key a first-class checkable artifact + a drain-order-replay
regression tripwire.
